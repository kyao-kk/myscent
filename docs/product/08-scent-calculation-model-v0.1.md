# MyScent 香味计算规则模型 v0.1

- 文档状态：Draft Concept Model
- 对应 Issue：#1
- 对应 PR：#2
- 适用阶段：P0-A 因果模型原型
- 上游文档：`02-mvp-prd-v0.2.md`、`04-scent-blocks-v0.1.md`、`07-mvp-prd-v0.2-review-v0.1.md`
- 可执行规格：`specs/scent/scent-engine.v0.1.json`
- 固定回归夹具：`specs/scent/scent-fixtures.v0.1.json`
- 目标：定义一个确定性、可解释、可版本化的数字香气预测模型，使玩家动作真实改变配方结果

> 本文保留模型原理、解释和设计依据。发生歧义时，以 `scent-engine.v0.1.json` 的执行顺序、公式、阈值与舍入策略为准。实现不得从本文自行推导另一套算法。

---

## 1. 模型定位

本模型不是：

- 真实分子级化学模拟；
- 对实际人体闻香结果的绝对预测；
- 由语言模型自由描述出来的香调文本；
- 可以直接替代试香和专业生产验证的公式。

本模型是：

> 一套基于香气积木属性、相对比例、阶段倾向、强度、互补、桥接、遮盖和冲突规则的数字香气计算系统。

它必须满足：

1. 同样输入、同样规则版本得到同样结果；
2. 改变材料或比例会产生可追溯变化；
3. 每项主要结果能指出证据；
4. 场景只改变表达，不改变计算；
5. 数据缺失时降低置信度，不编造确定结论；
6. 规则、参数和结果均可版本化与回归测试。

## 2. 标准尺度

### 2.1 内部数值范围

除特殊说明外，内部属性使用 `0.0 ～ 1.0`。

用户界面可转换为：

- 0～100；
- 低 / 中 / 高；
- 场景仪表、符号或视觉反馈。

### 2.2 八项核心属性

| 属性键 | 0.0 含义 | 1.0 含义 |
|---|---|---|
| sweetness | 不甜、干燥、苦 | 高甜、糖感、蜜感 |
| freshness | 沉闷、陈厚 | 清新、明亮、空气感 |
| warmth | 冷、凉、距离感 | 暖、热、包裹感 |
| weight | 轻盈、漂浮 | 厚重、浓密 |
| softness | 锐利、尖、干脆 | 柔和、圆润、顺滑 |
| transparency | 浑厚、不透明 | 透明、空灵、留白 |
| diffusion | 贴肤、低扩散 | 高扩散、存在感强 |
| longevity | 短暂、快速消散 | 长久、尾段支撑强 |

### 2.3 派生指标

- clarity：主体清晰度；
- complexity：结构复杂度；
- continuity：前中后段连续性；
- balance：整体平衡度；
- confidence：计算置信度。

派生指标不直接存入香气积木基础向量，由配方计算得出。

## 3. 香气积木参数结构

每个 `ScentBlock` 必须具有以下计算字段：

```json
{
  "id": "SB-CA-03",
  "version": "0.1",
  "family": "citrus_air",
  "attribute_vector": {
    "sweetness": 0.10,
    "freshness": 0.92,
    "warmth": 0.18,
    "weight": 0.12,
    "softness": 0.58,
    "transparency": 0.95,
    "diffusion": 0.62,
    "longevity": 0.22
  },
  "intensity": 0.75,
  "stage_weights": {
    "top": 0.80,
    "heart": 0.18,
    "base": 0.02
  },
  "role_tags": ["atmosphere", "opening", "brightener"],
  "data_quality": 0.85,
  "production_mapping_status": "unverified"
}
```

### 3.1 intensity

`intensity` 表示相同相对份数下，该积木对整体结果的潜在支配强度。

范围：`0.30 ～ 1.50`。

- 低强度积木需要更高比例才能成为主体；
- 高强度积木少量也可能产生明显影响；
- 不允许所有积木默认相同强度。

### 3.2 stage_weights

`top + heart + base = 1.0`。

表示积木在数字预测中的阶段倾向，不代表精确真实挥发曲线。

### 3.3 data_quality

用于置信度计算：

- 1.00：平台规则完整、组合测试充分；
- 0.70～0.99：基础数据完整，部分组合仍需验证；
- 0.40～0.69：实验性积木或映射有限；
- 0.00～0.39：用户自录或数据严重缺失。

## 4. 配方输入

### 4.1 相对份数

用户操作转换为非负相对份数 `q_i`。

归一化：

`p_i = q_i / Σq`

其中：

- `p_i` 为材料在当前数字配方中的归一化比例；
- `Σp_i = 1.0`；
- MVP 不将 `p_i` 直接宣称为真实生产百分比。

### 4.2 有效强度

直接使用比例会低估高强度材料，定义：

`e_i = p_i^γ × intensity_i`

P0-A 当前参数：

- `γ = 0.85`。

归一化有效贡献：

`n_i = e_i / Σe`

### 4.3 操作顺序

P0-A 默认：

- 添加顺序记录但不影响核心属性；
- 添加顺序用于操作回放、版本解释和未来工艺扩展；
- 不得在没有验证依据时声称“先加 A 再加 B 一定改变最终香味”。

---

## 5. 基础属性计算

对每个核心属性 `d`：

`A_base[d] = Σ(n_i × V_i[d])`

基础属性之后依次应用：

1. 遮盖对可感知贡献的修正；
2. 重新归一化；
3. 互补属性增益；
4. 桥接连续性增益；
5. 冲突惩罚；
6. 组过载规则；
7. 边界截断。

精确执行次序和公式以 `scent-engine.v0.1.json` 为准。

---

## 6. 前中后调计算

对阶段 `s ∈ {top, heart, base}`：

`C_i,s = perceived_e_i × stage_weight_i,s`

阶段内归一化：

`N_i,s = C_i,s / ΣC_s`

每个阶段输出：

- 第一主体；
- 第二主体；
- 其他辅助；
- 阶段总份额；
- 阶段清晰度；
- 是否不足或过度支配。

P0-A 当前阶段不足阈值为 `0.18`，主体与集中度阈值见可执行规格。

---

## 7. 主体与家族

全局贡献排序基于遮盖修正后的可感知贡献。

输出：

- primary_component；
- secondary_component；
- supporting_components；
- family_contributions；
- dominance_gap。

最终主香调同时参考：

- 单积木贡献；
- 家族总贡献；
- 角色标签；
- 遮盖关系。

---

## 8. 复杂度

使用：

- 归一化 Shannon entropy；
- 家族多样性；
- 当前命中的成对关系密度；
- 组规则复杂度修正。

当前公式：

`complexity = 0.55 × entropy + 0.30 × family_diversity + 0.15 × interaction_density + group_delta`

复杂不自动等于失败，必须和清晰度一起判断。

---

## 9. 清晰度

清晰度由以下部分构成：

- 主体差距；
- 主家族集中度；
- 前中后调连续性；
- 三阶段平衡；
- 主体未被遮盖程度；
- 冲突、主题过多和组过载惩罚。

当前公式和阈值以 `scent-engine.v0.1.json` 为准。

模型必须允许：

- 高复杂度 + 高清晰度；
- 低材料数量 + 低清晰度。

固定夹具 T-007 和 T-008 专门验证这两个情况。

## 10. 成对规则矩阵

### synergy 互补

提升指定核心属性，作用量基于两者较小可感知贡献。

### bridge 桥接

提升阶段连续性，不必直接提高核心属性。

### masking 遮盖

具有方向性。A 可以遮盖 B，但 B 不必同等遮盖 A。

遮盖先改变目标的可感知贡献，再进行重新归一化。

### conflict 冲突

降低派生清晰度或平衡度，必要时降低指定核心属性。

冲突不是安全禁用，也不是绝对不能组合。

## 11. 问题检测

P0-A 固定检测：

- 过甜；
- 过厚；
- 开场尖锐；
- 主体被遮盖；
- 中段缺失；
- 尾段不足；
- 主题过多；
- 冷鲜与暖甜拉扯；
- 成对冲突；
- 各组规则定义的问题。

每个问题必须提供：

- 问题代码；
- 证据；
- 影响材料；
- 影响指标；
- 最多 3 个可执行方向。

---

## 12. 建议生成

建议先由规则层生成标准动作，再由场景层翻译。

标准动作示例：

`decrease_component SB-GO-02 by one_step`

实验室表达：

> 将甜感组分下调一格。

魔法师表达：

> 收回一滴糖雾，让主药剂重新显形。

底层目标、证据和预期数值方向保持一致。

---

## 13. 置信度

置信度由以下部分构成：

- 数据完整度；
- 关系规则覆盖率；
- 材料映射质量；
- 是否处于已定义测试域；
- 当前版本稳定性。

等级：

- ≥ 0.80：高；
- 0.55～0.79：中；
- < 0.55：低。

用户自录材料缺少浓度、供应商或映射时，必须降低置信度，不能伪装成平台已验证结果。

---

## 14. 确定性与随机性

核心计算必须确定性：

- 同样输入；
- 同样引擎版本；
- 同样积木库版本；
- 同样关系库版本；

必须得到相同数值和公式哈希。

允许变化的只有：

- 解释措辞；
- 场景对白；
- 名称和香语候选；
- 海报和视频。

这些变化不得反向改写核心数值。

---

## 15. 输出契约

完整输出至少包含：

- formula revision 和 formula hash；
- 引擎、积木库和关系库版本；
- 归一化组件；
- 前中后调；
- 主体和家族贡献；
- 8 项属性；
- clarity、complexity、continuity、balance；
- 关系证据；
- 问题和建议；
- confidence；
- 预测声明版本。

前端不得通过解析自然语言重新推断结构化字段。

## 19. 参数变更治理

以下内容不得静默修改：

- γ；
- 积木向量、强度和阶段权重；
- 关系规则强度和阈值；
- 派生指标公式；
- 问题阈值；
- 置信度权重；
- 舍入和哈希策略。

任何变更必须：

- 新增版本；
- 更新夹具；
- 输出差异；
- 保留旧版本回放；
- 经过项目负责人确认。
